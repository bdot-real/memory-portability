\section{Evaluation}\label{sec:evaluation}

We ask how much of a user's memory survives a change of engine under ontology-mediated migration,
compared with carrying the transcript or an LLM-written summary, and where the loss happens.

\subsection{Portability Fidelity Metric}

Let $P$ be the set of primary probes of a persona, one per gold memory item. Each probe is a
question whose correct answer depends on that item. Migrating from source engine $A$ to target
engine $B$ under condition $k$ and probing $B$ gives
\begin{equation}
  \mathrm{PFM}^{k}_{A\to B} = \frac{1}{|P|}\sum_{p\in P}
    \mathbb{1}\left[\mathrm{score}\left(p,\ \mathrm{answer}^{k}_{A\to B}(p)\right)=\mathrm{correct}\right].
\end{equation}
We report \PFM averaged over personas, overall and per probe kind, with 95\% confidence intervals
from a bootstrap over personas (probes within a persona are correlated, so resampling probes would
understate the uncertainty).

\subsection{Dataset}

Personas are generated \emph{gold first}: a seeded generator fixes the memory items, then templates
the user's turns from them, so no LLM shapes the input and no engine family is favoured. Each
persona has a user, four related people and a pet, and about \res{items-per-persona} items spread
over sessions: facts about the user (home city, employer, occupation, language, \dots), facts about
the other people (occupation, allergy, home city), preferences with polarity and context, three
tasks with next steps, and three erasure requests (therapist, salary, ex-partner). Updates are
oversampled: the home city, employer, language, favourite dish and most task next steps change
once. Values are deliberately uncommon (small cities, invented employers, rare dishes) so that an
engine cannot answer from its priors, and within a persona no value is a substring of another.
All names are synthetic. Between memory-bearing turns, the dialogue carries small talk drawn from
a pool of 400 distinct lines. A \emph{small} tier has about \res{tok-small}k tokens of dialogue per
persona; a \emph{large} tier has the same items and probes padded to about \res{tok-large}k tokens,
still under 85\% of every engine's window.

The evaluation set has \res{n-personas-small} personas, generated from a seed never used during
development and played at both tiers, with \res{n-probes-small} probes per tier. The small tier ran
on an Apple M4 and the large tier on an NVIDIA T4 (Kaggle), with the same Ollama model digests.

\subsection{Conditions}

The dialogue is played on engine $A$, which replies live. After every session, each condition
updates its memory with the same cadence; then engine $B$ is probed in a fresh turn per question.
\begin{description}
  \item[\cond{a1} ontology via tools.] $A$ writes the store (Sect.~\ref{sec:adapters}); $B$
    queries it through the MCP tools.
  \item[\cond{a2} ontology rendered.] Same store; current items are rendered into $B$'s prompt.
  \item[\cond{b} transcript.] The full transcript, with session headers and dates, goes into $B$'s
    prompt.
  \item[\cond{c} summary.] $A$ keeps a running free-text summary, updated after each session and
    told to keep everything still true, with dates and session numbers.
  \item[\cond{oracle}.] The gold store, rendered as in \cond{a2}. It is an upper bound on what the
    representation and read-out can deliver, and the gap \cond{oracle}$-$\cond{a2} is the loss
    caused by $A$'s extraction.
  \item[\cond{a2x}, \cond{a1x} strong extractor.] As \cond{a2} and \cond{a1}, but the store is
    written from $A$'s dialogue by a larger hosted model with the same prompt and schema:
    Gemma~4 31B on the small tier and Claude Opus~5.5 on the large tier. The gap
    \cond{a2x}$-$\cond{a2} isolates the extractor.
\end{description}
Every context states the user's name, and all conditions share the same answering instructions.
Vendor-native memory export, a fourth baseline in principle, is not measured: none of the local
engines has native memory. We discuss it in Sect.~\ref{sec:discussion}.

We run all six ordered pairs of distinct engines. Same-engine pairs ($A=B$) are omitted: the
question is migration, and the oracle already bounds read-out without a change of engine.

\subsection{Probes and Scoring}

Primary probes cover four kinds: \emph{recall} (``What car do I drive?''), \emph{update} (``Which
city do I live in?'' after a move), \emph{multi-hop} over relationships (``If I cook for my
colleague, which ingredient must I leave out?'') and \emph{task} (``What is my next step on
renewing my passport?''). Scoring is deterministic: an answer is correct if it contains a gold
value (whole-word, case- and diacritic-insensitive) and no competitor. Competitors are explicit in
the gold: a superseded value alone scores \emph{stale}, another person's value \emph{distracted},
gold plus a competitor \emph{hedged}, a refusal \emph{abstained}. Mentioning the old value next to
the new one (``you moved from X to Y'') is correct.

Secondary probes are reported outside \PFM. \emph{Provenance} asks in which session an item was
stated. \emph{Null} probes ask about things never said and must be declined; anything else is a
false memory. \emph{Erasure} probes ask for an erased value (with spelling variants, e.g.\ 87500 and
87.5k); since a condition that remembers nothing passes trivially, each erasure probe is paired
with a recall probe on a non-erased user fact, and we report the leak rate only among cases where
that control was answered correctly. \emph{Preference application} (``Suggest a dinner for me and
my sister'') is scored by an LLM judge against a rubric: \texttt{phi4}, a fourth model family run
locally under a pinned digest, as the primary judge, and Gemma~4 31B (hosted) as a second rater.
Both judges also grade a stratified sample of deterministically scored answers, and a human labels
a blind subset of 200 answers. On the sampled deterministic answers, \texttt{phi4} agrees with
the scorer on pass versus not-pass for \res{agree-scorer-phi4-small} (small) and
\res{agree-scorer-phi4-large} (large) of answers (Cohen's $\kappa$ \res{kappa-scorer-phi4-small},
\res{kappa-scorer-phi4-large}). Most disagreement is on \emph{hedged} answers, which the scorer fails
and the judge often passes; without them agreement is \res{agree-scorer-phi4-nohedge-small} and
\res{agree-scorer-phi4-nohedge-large} ($\kappa$ \res{kappa-scorer-phi4-nohedge-small},
\res{kappa-scorer-phi4-nohedge-large}). On the \res{n-phi4-gemma-pref-small} preference answers
of the small tier, the two judges agree on \res{agree-phi4-gemma-pref-small} of verdicts
($\kappa$ \res{kappa-phi4-gemma-pref-small}): \texttt{phi4} is the stricter, passing
\res{pass-phi4-phi4-gemma-pref-small} of answers against \res{pass-gemma-phi4-gemma-pref-small}
for Gemma, so preference-application scores are best read as a lower bound and compared across
conditions rather than in absolute terms. \todo{judge--human agreement, once the labelled subset is
complete}

By kind (Table~\ref{tab:kinds}), the transcript's decline on long histories is concentrated in
updates and multi-hop questions, and it is mostly abstention rather than error: with the relevant
turns buried among many sessions, engines more often say they do not know, and somewhat more often
give the superseded value. Updates are the one kind where the engine-written store beats
the transcript on the large tier, because supersession is recorded explicitly at write-in and
read-out only sees current items. Tasks show the opposite: the transcript answers almost all of
them, while small engines rarely record next steps. By pair (Table~\ref{tab:pairs}), the target
engine matters more than the source for the transcript: \texttt{qwen2.5:14b} reads long
transcripts well, while \texttt{mistral:7b} and \texttt{llama3.1:8b} do not, and for
\texttt{qwen}$\to$\texttt{mistral} the engine-written store already beats the transcript.

On secondary probes, the gold store attributes items to the right session in nearly all cases
(provenance \res{provenance-oracle-large}, against \res{provenance-b-large} for the transcript),
and it never leaks an erased value (\res{leak-oracle-large}), while the transcript leaks
\res{leak-b-large} of erased values whose control item was recalled: an engine reading a
transcript sees both the value and the request to forget it, and does not always comply.

\paragraph{Strong readers.} To test whether the transcript's decline is a property of the
transcript or of the reader, we repeat the large tier with Claude Opus~5.5 and Haiku~5.5 as
target $B$, on the same cached dialogues, stores and summaries of the three local source engines
(Table~\ref{tab:strong-readers}). Both read the long transcript almost as well as the gold store
(Opus \res{pfm-b-opus-reader-large} against \res{pfm-oracle-opus-reader-large}; Haiku
\res{pfm-b-haiku-reader-large} against \res{pfm-oracle-haiku-reader-large}), so the transcript's
loss on long histories belongs to 7--14B readers. For strong readers the gold store's advantage is
cost, not accuracy. Neither strong reader lifts the stores written by small engines above
\res{pfm-a2-opus-reader-large}, which confirms that the ceiling there is extraction. Taken
together, the two experiments separate the roles: a strong model is needed once, at write-in,
after which a 7--14B reader of the store (\res{pfm-a2x-opus-large}, about
\res{ptok-a2x-large} prompt tokens per question) matches a frontier model reading the full
transcript (\res{pfm-b-opus-reader-large}, \res{ptok-b-large} tokens).

\subsection{Where Memory Is Lost}

\paragraph{Extraction.} Table~\ref{tab:extraction} compares each source engine's store with the
gold store, field by field. An extracted item matches a gold item when its class and identifying
fields agree (for a fact, the same subject and value). \emph{Lenient} recall only requires the
right subject and value in any class or field; the gap between the two is modelling disagreement
(an allergy stored as a fact rather than a preference that \texttt{Avoids}) rather than lost
information.

\paragraph{Tool use.} The gap between \cond{a1} and \cond{a2} reads the same store and isolates
the cost of reaching it through tools. We report tool calls per probe and the share of probes
answered without any call (\res{a1-nocall-rate-small} at both tiers). Engines differ sharply:
\texttt{mistral:7b} never called a tool, \texttt{qwen2.5:14b} called one for about three probes in
ten, and \texttt{llama3.1:8b} called one for almost every probe yet still scored below \cond{a2},
because its queries often missed the item. The tools themselves returned no errors; the loss is in
whether and how 7--14B engines look things up. Claude models, by contrast, called a tool for
every probe (\res{a1-calls-per-probe-opus-large} calls per probe) and reached
\res{pfm-a1-opus-reader-large} on the stores where rendering gives \res{pfm-a2-opus-reader-large};
small readers stay low even on strong-extracted stores (\cond{a1x} \res{pfm-a1x-opus-large}), so
tool use is a property of the reader, not the store. Rendering the store into the prompt (\cond{a2})
removes this loss and costs only a few hundred tokens, so it is the better read-out for small
engines; MCP read-out pays off when the store is too large to render.

\paragraph{Over-erasure.} Structured memory adds a failure mode that transcripts and summaries do
not have. An engine that applies an erasure request too broadly deletes true memories, and they
are gone for every future engine. On short histories \texttt{llama3.1:8b} wrote
\res{tomb-per-request-small} tombstones per requested erasure (Table~\ref{tab:extraction}), deleting
true memories each time a user asked to forget one thing.
Over-erasure should be measured whenever erasure is delegated to a model; in our architecture it
argues for keeping erasure a confirmed, user-initiated operation of the store rather than an
extraction output.

\subsection{Threats to Validity}

\emph{Synthetic dialogue.} Templated turns are repetitive and cleaner than real conversation. This
removes engine-family bias from the input at the cost of realism; a paraphrase pass by a model
outside the three families is a natural extension. \emph{Uncommon values} make guessing from priors
unrewarding, which may understate how much engines fill in from priors in real use. \emph{Small
models.} All engines have 7--14B parameters, chosen so the benchmark runs at no cost; the strong
strong extractors and readers are hosted. Gemma's weights are open but its serving is not pinned
by digest; Claude models are closed, served by model identifier only, and accept no sampling
temperature or seed at the settings we used, so their runs are not bit-reproducible. We release
their outputs and pair each Claude run with local engines only, so no engine reads memory written
by its own family.
\emph{Decoding failures.} Write-in replies are capped at 4096 tokens; on the large tier
\texttt{llama3.1:8b} hit the cap in \res{write-errors-llama-large} sessions, which count as lost
extraction. \emph{Hardware.} The tiers ran on different machines with the same model digests;
greedy decoding on different hardware can still differ in rare tokens. \emph{Tuning.} Prompts were tuned on a separate
development set, and every change is logged per condition; the summary and transcript baselines
received the same answering instructions as the ontology conditions. \emph{Scoring.} Deterministic
matching can miss a correct paraphrase (e.g.\ a number written in words); \todo{report the
disagreement rate on the human-labelled subset}. \emph{Version drift.} Models are pinned by Ollama
tag and digest, and all outputs are released.
